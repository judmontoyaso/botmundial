# 1. Sitios web y APIs para scraping

**Estadísticas generales.** Muchos sitios ofrecen datos estáticos (tabla, resultados, clasificaciones) fáciles de scrapear, mientras que otros son dinámicos y requieren técnicas avanzadas. Por ejemplo, **Transfermarkt** tiene “*no anti-bot protection*” y páginas en HTML plano【3†L216-L223】, por lo que es relativamente sencillo extraer plantillas, historial de jugadores, precios de mercado, etc. En cambio, **SofaScore** emplea fuertes medidas anti-bot: su página de partidos carga datos mediante llamadas internas. Una solución típica es simular un navegador: un ejemplo de Python usa *Playwright* para “calentar” la sesión en sofascore.com (recolectar cookies/tokens) y luego invocar su API interna【8†L131-L139】. De forma similar, **Flashscore** es muy dinámico y “requiere evadir complejos mecanismos anti-bot”【10†L185-L193】, por lo que suelen usarse Selenium o APIs de terceros. **WhoScored** también se basa en JavaScript: bibliotecas como *soccerdata* recomiendan usar proxies o Selenium para no ser bloqueados【14†L73-L82】【14†L100-L107】. **FBref** (datos de StatsBomb) dispone de tablas HTML, pero parte de la información (segunda tabla de estadísticas) solo aparece ejecutando JavaScript【16†L214-L223】, por lo que conviene usar un navegador headless. Sitios más sencillos como **Soccerway** ofrecen endpoints JSON ocultos (por ejemplo `nr.soccerway.com/a/block_team_matches` para resúmenes de partidos【22†L145-L154】) que pueden explotarse en lugar de parsear HTML bruto. **FotMob** y similares (p.ej. **FotMob**) suelen requerir Selenium, aunque hay librerías que utilizan sus APIs internas (por ejemplo *PyFotMob* accede directamente al API de FotMob, evitando el scraping)【19†L83-L92】. En cambio, páginas como **365Scores** o **ESPN FC** pueden consultarse vía API pública: por ejemplo, *soccerdata* aprovecha la API de ESPN (`site.api.espn.com`) para obtener calendarios, estadísticas y alineaciones【25†L50-L59】. 

**Métricas avanzadas.** Sitios especializados de métricas derivadas suelen exponer datos en JSON. **Understat** es ejemplo clásico: hay endpoints JSON (por liga, equipo, jugador) que devuelven estadísticas avanzadas (xG, tiros esperados, etc.). Una API de usuario confirma que se llaman rutas como `/league/{nombreLiga}`, `/team/{equipo}/{temporada}`, etc., devolviendo JSON con xG y datos de partido【27†L119-L128】. **StatsBomb Open Data** ofrece JSON gratuitos (en GitHub) con datos de eventos, alineaciones y estadísticas avanzadas para campeonatos seleccionados; p.ej., incluye carpetas `matches/`, `events/`, `lineups/` con archivos por partido【29†L265-L273】. En contraste, **Opta** (StatsPerform) y **Wyscout** son propietarias: Opta obtiene datos “en tiempo real” mediante analistas y visión por computadora【104†L393-L402】, pero no hay forma pública de scrapearlos (hay que comprarlos). También hay bases comunitarias en Kaggle (p.ej. la “European Soccer Database” con 25k partidos y 10k jugadores【34†L19-L27】) y repositorios open-source. 

**Odds y apuestas.** Los sitios de cuotas suelen ser dinámicos. **OddsPortal** y **BetExplorer** exigen Selenium para cargar el DOM completo: por ejemplo, un scraper de OddsPortal usa ChromeDriver para navegar y extraer tablas de cuotas【37†L268-L277】. En BetExplorer incluso hay que “hacer scroll hasta el final” para renderizar todo el contenido【121†L272-L280】. Para casas como **Pinnacle**, existe una API oficial (JSON) pero actualmente cerrada al público【49†L259-L268】; en cambio, **Bet365** no ofrece API gratuita y su sitio es muy complejo (muchos han tenido que reconstruir sus llamadas internas). Una alternativa es usar API agregadoras de cuotas: por ejemplo *The Odds API* (the-odds-api.com) ofrece un feed JSON con cuotas de varias casas【44†L210-L213】, aunque es de pago. En general, las cuotas (“moneyline”, en 1X2 o hándicap) se suelen obtener vía scraping con Selenium o mediante APIs especializadas. 

**Noticias y contexto.** Sitios de noticias deportivas (**FIFA.com**, **UEFA.com**, **Goal.com**, **Marca**, **ESPN**, **BBC Sport**, etc.) tienen contenido mayormente estático y pueden scrapearse con BeautifulSoup o extraerse de feeds RSS (p. ej. BBC Sport Football ofrece un RSS actualizado por minutos【51†L24-L33】). **The Athletic** suele estar detrás de paywall, pero medios libre como BBC/Marca/Goal son accesibles (respetando TOS). Redes sociales y medios alternativos (Twitter/X, Reddit, YouTube) requieren APIs o scraping más complejo: la API oficial de X hoy está muy limitada, por lo que se puede recurrir a scrapers de páginas públicas con rotación de proxies o a soluciones de terceros; Reddit sí ofrece una API pública para leer subreddits (p.ej. r/soccer) donde extraer comentarios y sentimientos. Los transcripts de YouTube (charlas técnicas, ruedas de prensa) pueden extraerse con librerías de texto de video (youtube-transcript-api). En resumen, estas fuentes contextuales se usan para señales de ánimo (p.ej. tendencias de Twitter) o noticias de último minuto (lesiones recientes, polémicas), aunque su scraping es más frágil y sujeto a cambios de política. 

**Lesiones y alineaciones.** Páginas dedicadas existen: **Transfermarkt** tiene sección de lesiones por jugador y por liga; por ejemplo, la función *tm_league_injuries()* de *worldfootballR* extrae “todas las lesiones actuales reportadas” de la liga española【54†L218-L226】. **Rotowire** ofrece un feed RSS de noticias de fútbol (incluye actualizaciones de lesiones)【56†L149-L153】. Para alineaciones, **SofaScore** y **FotMob** son útiles: SofaScore expone un endpoint JSON por partido (`/event/{id}/lineups` tras obtener el ID del evento)【64†L183-L188】. FotMob publica en su web listados de alineación y lesiones; por ejemplo, su página de equipo muestra jugadores con anotaciones de lesión (“Thigh injury – Out for season” en texto claro【62†L19-L27】). En todos los casos suele ser necesario renderizar (Javascript) o usar sus APIs internas. 

**Datos alternativos.** Señales poco convencionales también pueden ayudar. Datos meteorológicos (p.ej. **OpenWeatherMap** o APIs de clima) permiten incluir temperatura, lluvia, humedad para cada partido. La altitud del estadio es especialmente relevante: un estudio de la BMJ muestra que equipos de alta montaña (Bolivia vs Brasil, ≈3695 m) tenían 82.5% de probabilidad de ganar en casa frente a solo 53.7% en nivel de mar【116†L60-L64】. También se considera distancia de viaje o zonas horarias para fatiga, usando geoposicionamiento (estadio vs ciudad visitante). Indicadores sociales como Google Trends o “momentum” en redes pueden extraerse (p.ej. series temporales de búsquedas de un equipo o sentimiento en Twitter). Estas fuentes alternas se usan para modelar factores como motivación, atención de los fans o efectos ambientales, aunque suelen tener señal débil comparada con estadísticas deportivas.

# 2. Datos específicos extraíbles

**Equipos.** De los sitios anteriores se puede obtener la forma reciente (ultimos resultados, puntos en X partidos), tendencia ofensiva/defensiva, posesión media, tiros totales y contraataques (de SofaScore/FotMob), goles esperados promedia (xG) y en contra (xGA) de Understat o StatsBomb, así como métricas de intensidad de presión como PPDA (si se dispone de posición de balón, p.ej. por Pypots o StatsBomb). El estilo táctico (posesión vs contraataque) a veces se infiere de estadísticas agregadas (porcentajes de pases, pressing alto, pases largos) o de etiquetas de prensa. El rendimiento en casa/afuera es básico (puntos por partido local/visitante). También puede extraerse la eficacia ofensiva (goles por tiro dentro del área) y defensiva (disparos concedidos vs bloqueados). Historial reciente contra rivales “top” se computa con filtros (p.ej. estadísticas solo contra equipos en top-6 de liga). Finalmente, los resultados históricos (tabla, enfrentamientos directos) se encuentran en Soccerway, FBRef, Transfermarkt o bases como football-data. En general, estadísticas basadas en xG, diferencial de tiros y goles (indicando calidad de chances) han demostrado mayor valor predictivo, mientras que métricas superficiales como posesión bruta suelen aportar poco aisladas (los estudios muestran que los equipos ganadores controlan más el balón en promedio【67†L1-L4】, pero la posesión en sí no asegura goles). 

**Jugadores.** De Transfermarkt/FBRef/SofaScore se extraen minutos jugados, goles, asistencias, valor de mercado, edad y posición. El historial de lesiones (días fuera) indica disponibilidad. StatsBomb/Understat ofrecen xG individual (goles esperados generados por el jugador) y asistencias esperadas, pases progresivos completados, duelos (aéreos, defensivos) ganados, etc. Medidas de presión defensiva (p.ej. recuperaciones o tackles) pueden extraerse si el proveedor lo ofrece. También se pueden computar mapas de calor de participación (con datos posicionales en algunos feeds). Variables más abstractas como “química” entre jugadores no suelen estar disponibles explícitamente; a lo sumo se pueden inferir comparando lineups (p.ej. porcentaje de partidos compartidos en el campo). Al final, las estadísticas por competición (liga, copa, selección) permiten ver si un jugador rinde mejor en ciertas condiciones. De todos estos, lo más relevante suele ser el aporte ofensivo (goles, asistencias, xG) y la consistencia (minutos, forma reciente). Datos como edad o valor de mercado son proxies de calidad general. El desgaste (‘fatiga’) se cuantifica usando minutos acumulados o partidos seguidos sin descanso. Muchos modelos priorizan características sencillas (estrellas en alineación, goles recientes), ya que indicadores complejos (p.ej. duelos defensivos) solo aportan si están correctamente normalizados.  

**Partido.** Factores contextuales incluyen el clima (temperatura, lluvia, nieve), extraídos de APIs meteorológicas; la altitud del estadio (impacto en oxigenación)【116†L60-L64】; e información logística (hora local, diferencia horaria viajada). Otros datos: identidad del árbitro (p.ej. tasa de amonestaciones por árbitro, que se puede extraer de lecturas pasadas de cada referí), asistencia de público (reportada por FIFA/estadísticas oficiales), presión mediática previa (p.ej. volumen de noticias sobre el partido) y las cotizaciones iniciales de las casas de apuestas (impliquen probabilidades). También se incluyen noticias previas al partido (alineaciones probables, lesiones de último momento) y sentimiento social (tendencia de Twitter hacia un equipo). De estos, factores como el clima extremo o la altitud sí tienen probada influencia【116†L60-L64】, así como las cuotas de apuestas (contienen casi todo el know-how del mercado). En contraste, indicadores cualitativos (“tensión mediática”, “sniper momentum”) son más difusos. Un ejemplo concreto: estudios han encontrado que el sentimiento agregado de tweets sobre los equipos predice diferencias de goles y rinde mejor que apostar siempre al favorito【86†L83-L92】【86†L91-L94】, lo que sugiere que estas señales micropsicologicas pueden capturar algo de información adicional. 

# 3. Técnicas modernas de scraping

Para obtener datos de sitios web actuales se usan diversas herramientas:

- **BeautifulSoup / Requests**: útiles cuando la página está en HTML estático. Se descarga el HTML y se parsea con BS4. Rápido y ligero, pero no ejecuta JavaScript. Bueno para sitios simples como Transfermarkt o páginas de noticias.

- **Scrapy**: framework Python para crawling masivo. Permite gestionar *pipelines*, rotar user-agents y proxies, definir reglas de extracción y manejar cola de tareas. Ideal para scraping intensivo (múltiples ligas/temporadas) de sitios relativamente estáticos. Soporta middleware de rotación de proxies/UA. 

- **Selenium / Playwright**: emulan navegadores reales. Selenium (con Chrome/Firefox) o Playwright abren páginas completas y ejecutan JavaScript, por lo que son necesarios para SofaScore, Flashscore, BetExplorer, etc. Permiten, p.ej., “scroll” la página o hacer clic antes de extraer contenido. Playwright es más moderno (soporta headless Chrome, manejo automático de contexto). Como una guía señala, para SofaScore se lanza el navegador completo con Playwright “para evitar medidas anti-bot avanzadas que bloquean scripts simples”【8†L131-L139】. Selenium/Playwright permiten cargar las APIs internas (al abrir la web) y luego llamar las URLs JSON con `driver.get()`.

- **Requests-HTML / Pyppeteer**: híbridos que combinan Requests con un browser embebido. Pueden ejecutar algo de JavaScript. Útiles cuando BS4 falla por scripts ligeros. 

- **Rotating proxies / VPNs**: para no ser bloqueado por límite de peticiones. Se recomienda usar tor o redes de proxies comerciales que roten IPs, especialmente en scraping masivo (p.ej. SofaScore y WhoScored requieren múltiples IPs【14†L73-L82】).

- **Rotación de User-Agents**: alternar cabeceras entre distintas navegadores (Chrome, Firefox, móviles) imitando tráfico humano.

- **Evitar detección anti-bots**: además del propio navegador, se pueden emplear servicios de resolución de CAPTCHA o soluciones como *undetected-chromedriver*. También se usa *rate limiting* (esperar random entre peticiones) para parecer humano.

- **Scraping distribuido**: orquestar múltiples instancias simultáneas (p.ej. con Celery + Redis) para paralelizar la recolección en varias IPs. 

- **Scraping incremental**: mantener registros de fecha/ID de último dato extraído y solicitar solo lo nuevo (por ejemplo, solo partidos jugados desde la última fecha).

- **Caché y deduplicación**: guardar copias locales (o en S3) de respuestas previas para evitar peticiones repetidas. Verificar si la página cambió (hash) antes de procesarla.

- **Manejo de errores y CAPTCHAs**: implementar reintentos con backoff, alertar si aparece CAPTCHA. Usar servicios de reconocimiento de CAPTCHA solo como último recurso, pues suelen ser costosos.

En conjunto, una estrategia real podría combinar: Scrapy para colecciones rutinarias (por ejemplo, partidos históricos) y Selenium/Playwright para páginas difíciles (cuotas en vivo, plantillas). Siempre con proxies rotativos y delay aleatorio. Para *scraping masivo* a múltiples sitios, se desplegarían múltiples workers en la nube; para *datos diarios/near-real-time* se usarían tareas agendadas (cron/Airflow) que llamen APIs (de The Odds API, StatsBomb, etc) o scrapers controlados. La resistencia se logra detectando fallos: por ejemplo, si la estructura HTML cambia, se avisa para actualizar el scraper. 

# 4. Arquitectura de pipeline profesional

Un pipeline de datos deportivos robusto suele incluir varias capas:

- **Orquestador y scheduler**: usar Apache Airflow (o Prefect) para programar tareas diarias/semanales. Airflow permite dependencias entre tareas, reintentos automáticos y **“data-aware scheduling”** para ejecutar pasos solo cuando llegan nuevos datos【80†L123-L132】. También se puede usar Celery (con Redis/RabbitMQ) para distribuir trabajos de scraping en paralelo. Kafka puede usarse si hay streams de datos en tiempo real (p.ej. apuestas en vivo).

- **Detección de cambios**: un módulo que compare versiones de las páginas (o datos fuentes) con lo anterior, enviando alertas si cambian los selectores o estructura HTML.

- **Almacenamiento raw**: guardar los datos sin procesar (HTML, JSON) en un data lake (p.ej. buckets S3). Se versionan con timestamps. De esta forma siempre hay histórico completo.

- **Normalización y limpieza**: convertir datos diversos a un formato común. Ejemplo: estandarizar nombres de equipos (variaciones en distintos sitios), convertir fechas a un mismo timezone, imputar valores faltantes. Esto suele hacerse con scripts de Python o en etapas Airflow. Los datos “limpios” van a una base más estructurada (p.ej. PostgreSQL, o archivos Parquet en S3 con esquema definido).

- **Deduplicación y merges**: combinar las mismas entidades obtenidas de múltiples fuentes (p.ej. un partido que aparece en SofaScore, FotMob y ESPN) usando llaves únicas (fecha, local, visitante) y eliminando redundancias. También generar nuevos IDs persistentes.

- **Feature engineering**: calcular variables derivadas (p.ej. promedios móviles de xG, distancia de viaje, indicadores de forma). Estos cálculos pueden hacerse en SQL en una base relacional o con DuckDB/Pandas sobre los datos normalizados. Se suele almacenar el resultado final en tablas intermedias.

- **Versionado de datos**: cada corrida del pipeline produce versiones de los datasets (por ejemplo, por torneo y fecha). Se pueden usar git para metadatos o almacenar snapshots de tablas.

- **Almacenamiento analítico**: guardar los datos listos para modelado en formatos columnar (Parquet) dentro de un data warehouse o incluso en DuckDB sobre S3. DuckDB permite definir tablas virtuales sobre URLs S3【83†L163-L170】, facilitando análisis rápidos sin mover datos.

- **Monitorización y alertas**: se deben registrar logs (errores de scraping, latencias) y montar paneles (Grafana, etc). Alertas automáticas (por email/Slack) ante fallos críticos (caídas de sitios, robots bloqueados).

Por ejemplo, un equipo de MLB describió que utiliza Airflow para coordinar la ingesta de múltiples fuentes (sensores, clima, datos de juego) y asegura que “los pipelines se ejecuten solo cuando ciertos datos han sido actualizados”【80†L109-L118】【80†L123-L132】. En la capa de almacenamiento, se recomienda la arquitectura *medallion*: **Bronze** (datos crudos en S3), **Silver** (datos transformados y limpiados), **Gold** (agregados finales para ML)【83†L62-L70】. DuckDB facilita consultas analíticas directamente sobre los archivos Parquet en S3 (creando tablas externas sobre URLs)【83†L163-L170】. En resumen, usar Airflow (o Prefect) + Celery para workflows, Kafka/Redis para mensajería, S3/Parquet para almacenamiento escalable, PostgreSQL/DuckDB para análisis estructurado, y librerías Python (Pandas, SQL) para procesamiento intermedio. 

# 5. De scraping a features predictivas

Convertir datos crudos en señales útiles requiere ingeniería de características:

- **Noticias → sentimiento/tópicos:** Se puede procesar textos de noticias, tweets o declaraciones con NLP. Por ejemplo, extraer un *sentiment score* con un modelo preentrenado (VADER o un BERT afinado) para los titulares pre-partido, asignando un valor numérico al “ánimo” de cada equipo. Otra opción es obtener *embeddings* de oraciones (usando un modelo como Sentence-BERT) de artículos tácticos o comentarios de expertos, y luego usar distancia coseno o técnicas de clustering para resumirlos. Un estudio encontró que el sentimiento agregado de tweets de aficionados predijo diferencias en el resultado【86†L83-L92】【86†L91-L94】: esto sugiere que señales de texto agregadas pueden capturar factores no evidentes en las estadísticas puras.

- **Lesiones → impacto esperado:** A partir del scraping del estado físico de jugadores clave, se crea una métrica de “efecto lesión”. Por ejemplo, si el goleador titular está lesionado, podemos estimar que el equipo pierde X% de su capacidad goleadora. Esto se puede cuantificar usando la media de goles/partidos de ese jugador. En ML, se puede incluir una feature binaria o continua (minutos perdidos) por posición importante. Se puede incluso calibrar el efecto observando partidos anteriores con lesiones similares (meta-analizando la caída en goles esperados).

- **Alineaciones → estabilidad/riqueza táctica:** Un enfoque es calcular un *score de estabilidad de XI*: porcentaje de jugadores habituales que repiten del último partido o del promedio de temporada. Un cambio brusco (muchos suplentes) indica falta de ritmo. También puede calcularse una similitud entre alineaciones (p.ej. usando índice de Jaccard de la lista de titulares). Otra idea: ponderar la experiencia combinada del once (suma de minutos jugados juntos). Estas características cuantifican la cohesión del equipo. 

- **Odds → probabilidad implícita:** Las cuotas se transforman a probabilidades imponiendo normalización (quitando la margen del bookie). Ejemplo: si la cuota decimal es 2.50, la prob implícita es 40%. Este valor se puede usar directamente como variable (“probabilidad pre-partido”) o combinada con otras señales. Dado que las casas integran mucha información, la probabilidad implícita es a menudo el predictor más fuerte. De hecho, en estudios de apuestas el pronóstico del favorito usualmente rinde mal en ganancias relativas, lo que pone de relieve que las cuotas contienen ya un consenso exhaustivo de datos y expertos【86†L83-L92】. 

- **Tácticas/Reseñas → embeddings:** Los comentarios de entrenadores y análisis tácticos pueden procesarse con modelos de lenguaje. Por ejemplo, un LLM puede extraer temas (“presión alta”, “juego de posesión”, “defensa en zona”) de un artículo previo al partido, convirtiéndolos en features (categorías o vectores de embedding). Se pueden aplicar pipelines de NLP (Topic Modeling, embeddings de Transformers) sobre textos de prensa para incorporar la “dirección estratégica” reciente de un equipo. 

- **Redes sociales → momentum psicológico:** Aparte de sentimiento, se puede medir el *engagement* o “borboteo” social. Un ejemplo es contar volumen de menciones o hashtags específicos antes/durante el partido. Más sofisticado, se puede usar Twitter Streaming para obtener un embedding contextual de la discusión (usando modelos de lenguaje) y resumirlo a un indicador de “optimismo de fans”. Estudios muestran que las métricas sociales aportan información extra – un equipo con alto hype positivo tiende a superar predicciones basadas solo en estadísticas puras【86†L83-L92】. 

En todos estos casos se recurre a técnicas de NLP: tokenización, vectores TF-IDF o mejor, embeddings contextualizados (BERT, GPT, etc.). Para señales numéricas (lesiones, odds, alineaciones), se integran directamente como features numéricas o categóricas. A veces se construyen “features combinadas” (por ejemplo, producto de confianza de alineación por probabilidad implícita) para capturar interacciones. En resumen, hay que transformar información textual y cualitativa en variables cuantitativas (sentiment score, embeddings, indicadores binarios) que luego ingrese al modelo predictivo. 

# 6. Conjuntos de datos históricos gratuitos

- **Kaggle**: aloja múltiples datasets comunitarios. Un ejemplo es la “European Soccer Database” (25k+ partidos, 10k jugadores desde 2008)【34†L19-L27】, con resultados, alineaciones y goles. Otra colección célebre es *Football.csv* (de footballdata). En general, estos están en CSV o SQLite, son fáciles de usar pero varían en calidad (depende del curador) y cobertura (muchos se concentran en Europa).

- **StatsBomb Open Data**: ya mencionado en la sección de scraping. Es uno de los mejores para análisis avanzado ya que incluye datos de eventos jugada por jugada para partidos (varias ligas, copas, Mundial, etc). La calidad es profesional. El contra es la *cobertura limitada* (solo las ligas seleccionadas que StatsBomb liberó, no todas). Sin embargo, los eventos echan mano a machine learning al ofrecer granularidad (posesión con coordenadas, tipos de pase, etc.) apta para modelos sofisticados.

- **FiveThirtyEight SPI**: provisto en un R-package o GitHub. SPI (Soccer Power Index) asigna a cada equipo valores globales de ataque, defensa y una calificación total. Por ejemplo, la tabla SPI tiene columnas `off`, `def`, `spi` junto a nombre y ranking mundial de clubes【91†L32-L40】【91†L50-L58】. No contiene partidos, solo rating de equipos en una temporada. Útil como feature de fuerza relativa, pero no describe eventos o momentos de juego. 

- **football-data.co.uk**: Página clásica para apostar. Descarga CSV con resultados históricos (local/visitante, goles) de muchas ligas europeas desde 1993/94【93†L170-L178】. Para algunas ligas mayores también incluye estadísticas (tiros, corners, faltas, tarjetas) desde 2000 en adelante【93†L170-L179】. Además registra cuotas de apuestas (hasta 10 casas) a lo largo de cada temporada【93†L177-L184】. Estos CSV son de muy fácil uso (carga directa en Pandas) y han sido ampliamente usados en ML deportivos. Su calidad es buena (proyectos de años de benchmarking las usan), aunque no hay eventos detallados (ni xG).

- **openfootball (aka worldfootball)**: Repositorio de textos con calendarios y resultados de muchos torneos internacionales (Copas del Mundo, Ligas históricas, Eurocopa, etc.). Por ejemplo, la World Cup 2014 se almacena en formato legible (Football.txt) con fechas, equipos, marcadores y goleadores【95†L116-L124】. La cobertura es amplia (varios mundiales, Eurocopas, ligas populares), pero los datos son simplemente resultados y algunos detalles (goleadores, árbitros), no estadísticas avanzadas. Fácil de parsear con scripts sencillos.

- **Base mundialista de Fjelstul (worldcup, GitHub)**: recopilación muy completa del historial de Copas del Mundo (masculina y femenina). Incluye tablas relacionales de torneos, equipos, partidos, jugadores, alineaciones, además de eventos (todos los goles, faltas, penales, etc. de cada partido)【102†L1-L4】. Los datos vienen en CSV, JSON y SQLite. Es de muy alta calidad para estudios históricos de mundial; cubre desde el primer Mundial hasta hoy en día. Su granularidad es excepcional (puedes reconstruir completamente cada partido), aunque está limitado a los mundiales. 

En resumen, estos conjuntos son gratis y fáciles de usar (CSV/JSON), pero cada uno tiene limitaciones de cobertura. Para ML, **football-data** y **StatsBomb** son especialmente útiles: el primero por amplitud de ligas/historial, el segundo por detalle de eventos. **Kaggle/openfootball** son buenos complementos (fácil acceso), y **SPI** sirve como línea base de ranking de equipos. 

# 7. Prácticas de empresas (Opta, SofaScore, bookies)

- **Opta / StatsPerform**: Recopilan datos mediante analistas humanos y visión por computadora en tiempo real【104†L393-L402】. Generan estadísticas cada instante (pases, tiros, entradas, xG, etc.) con alta precisión. Estas métricas “enriquecidas” (expected goals, expected assists, PPDA, etc.) se usan internamente y por medios. También ofrecen productos analíticos (Opta Points, Opta Predictions), aunque los detalles de sus algoritmos son propietarios. En general, Opta “provee todo, desde el marcador hasta estadísticas profundas y predicciones de torneo”【104†L393-L402】. Por tanto, métricas como xG provienen de su posprocesamiento de los datos de evento. Se infiere que su rating de jugadores (p.ej. Opta Index) combina rendimiento con peso según influencia histórica.

- **SofaScore**: Utiliza datos detallados (posiblemente de Opta/StatsBomb) y aplica su propio algoritmo de calificación de jugadores (similar al «goal impact» de EA o índice TyCS por ejemplo). No es público, pero se sabe que considera acciones efectivas (goles, pases clave) y el rendimiento medio. A menudo confirma alineaciones, lesiones, formaciones (como vimos). Su “Power Rank” o rating de equipo se basa en las estadísticas en tiempo real y resultados recientes. Técnicamente, extraen datos en vivo de los feeds que usan en su app (p.ej. el endpoint `api.sofascore.com`), los ponderan y generan sus índices.

- **Bookmakers**: Combinan modelado estadístico propio con ajustes manuales. Un foro explica que los **oddsmakers** analizan “historial, forma, lesiones, dinámica de equipo” y también usan algoritmos avanzados para generar cuotas iniciales【107†L125-L133】【107†L133-L142】. Luego ajustan las probabilidades en tiempo real según el flujo de apuestas y la prensa【107†L145-L153】. En la práctica, muchos emplean modelos Poisson o basados en ELO para predecir resultados, luego añaden su *vig* (margen de beneficio). Los “sharp bettors” y el mercado mueven las cuotas: si llega mucho dinero por un resultado, los algoritmos las corrigen rápidamente【107†L135-L142】【107†L145-L153】. En resumen, las casas manejan señales muy similares a las de un analista (resultados previos, localía, noticias) pero codificados en sofisticados sistemas que equilibran la probabilidad real y la rentabilidad, incluyendo sesgos de mercado. Esto explica por qué las probabilidades implícitas de los bookies suelen ser la mejor referencia para ganar partidos: incorporan, en forma cuantitativa, casi todas las variables relevantes (las estadísticas de los jugadores, el factor casa, las lesiones reportadas, las condiciones del partido e incluso la psicología del mercado).

# 8. Recomendación final

Para un proyecto de predicción para un Mundial, conviene priorizar fuentes con alta calidad y señal:

- **Fuentes esenciales para scraping:** **Transfermarkt** (rosters, lesiones, forma)【3†L216-L223】【54†L218-L226】, **Understat** (xG / desempeño por equipo/jugador)【27†L119-L128】, **StatsBomb Open Data** (eventos detallados)【29†L265-L273】, **football-data.co.uk** (resultados históricos y cuotas)【93†L170-L178】【93†L177-L184】, **FIFA/WorldCup DB** (registro completo de Copas del Mundo)【102†L1-L4】, y quizá **soccerway** o **openfootball** para calendarios/resultados extra. 

- **APIs recomendadas:** Usar todo API oficial posible (p.ej. ESPN API para resultados actuales【25†L50-L59】, **FotMob API** vía librería *PyFotMob*【19†L83-L92】 para calendarios y estadísticas de partidos, **The Odds API** para cuotas). Si se dispone de presupuesto, contratar feeds oficiales (StatsPerform, SportRadar) acelera el desarrollo. 

- **Combinación óptima de fuentes:** Mezclar datos *macro* (resultados/historial de transfermarkt, SPI de Fivethirtyeight【91†L32-L40】【91†L50-L58】) con *micro* (eventos de StatsBomb/Understat, cuotas, noticias). Por ejemplo, usar xG de Understat como predictor principal, junto con mercado de apuestas para calibrar, e incorporar sentimiento social para refinar en partidos con información explosiva reciente. 

- **Datos con más ventaja:** Las métricas basadas en goles esperados y rendimiento real (xG, disparos al arco, diferencia de goles) suelen ser los predictores más sólidos. Las probabilidades de apuestas (odds) son otra señal clave, pues sintetizan toda la información relevante. También es valiosa la información de lesiones/clasificaciones de FIFA (que se puede usar para ajustar fuerza de equipos). Datos contextuales extremos (clima severo, altitud alta【116†L60-L64】) deben incluirse si corresponden.

- **Características a priorizar:** *Diferenciales de xG* en últimos partidos, *puntos por partido* recientes, *rating de equipo (ELO/SPI)*, *probabilidades implícitas de victorias*, *ventaja de local*, y *presencia/ausencia de estrellas*. También el *estado de forma* (puntos en los últimos 5 encuentros) y variables tácticas sencillas (p. ej. media de posesión ajustada, número de pases clave). 

- **Qué evitar:** Estadísticas superficiales o muy correlacionadas (por ejemplo, possession %) aportan poco extra tras considerar xG. Fijarse excesivamente en datos ruidosos (como química de equipo no medida) o fuentes no confiables (blogs sin datos duros) puede introducir sesgo. Tampoco conviene saturar el modelo con variables similares (p. ej. goles y xG a la vez pueden redundar; se elige la más robusta).

- **Pipeline robusto para startup:** Empezar simple: un script en Python para descargar CSV de football-data.co.uk y JSON de APIs de Understat/StatsBomb, programado con un scheduler (cron o Airflow gratuito) y almacenado en un bucket S3 (o base de datos SQLite/DuckDB local). Con el tiempo, migrar a Airflow o Prefect para escalar. Usar Parquet y DuckDB como soluciones livianas de almacenamiento/consulta. Para poca infraestructura, puede usarse Heroku/Google Cloud Run con tareas cron. Priorizar calidad: validar siempre cada lote scraping (ej. comparando recuentos, hashes). Una startup pequeña debe enfocarse en fuentes gratis: understating (no valga la pena pagar Opta de entrada), Kaggle/OpenFootball para cargar históricos, y The Odds API o webs equivalentes para predicción. 

En conclusión, la clave es equilibrar: **fuentes robustas y bien estructuradas** (analizar antes de scrapear, preferir APIs o endpoints JSON) y **características con sustento estadístico** (xG, probabilidades). Se sugiere construir un pipeline modulado (por liga, por tipo de dato) con claras etapas de control de calidad y un repositorio de datos versionado. Los sitios más recomendados a scrapear son Transfermarkt (alineaciones, lesiones, transferencias), Understat (estadísticas avanzadas), SofaScore/FotMob (estudios de partidos) y football-data.co.uk (histórico y odds)【3†L216-L223】【27†L119-L128】【93†L170-L178】. APIs como ESPNs, PyFotMob, TheOddsAPI aportan estabilidad. Priorice features de alto contenido predictivo (diferencial de xG, odds implícitas, indicadores de forma) y evite ruido innecesario. Con esta combinación y una arquitectura de scraping/ETL sólida basada en tecnologías como Airflow, S3/Parquet y DuckDB【80†L109-L118】【83†L62-L70】, incluso un equipo pequeño puede montar una plataforma fiable de predicción para el Mundial 2026.
